Patterns

Recipes

Recipes show how VDS components compose into common product flows. They are not runtime frameworks: application code owns data, routing, validation, keyboard behavior, and announcements.

Source truth

Recipe imports

Recipes combine authored CSS under src/components/ and package-facing imports under dist/components/. Import only the surfaces the page uses. 

@import "@24vlh/vds/dist/core.css";
@import "@24vlh/vds/dist/components/header-footer.css";
@import "@24vlh/vds/dist/components/forms.css";
@import "@24vlh/vds/dist/components/tables.css";
@import "@24vlh/vds/dist/components/feedback.css";

Runtime ownership

Recipe boundaries

Recipes are copy-safe starting points, not complete applications.

  • App shell recipes own navigation, active route state, search, and responsive menu behavior.
  • Form recipes own labels, validation, submission, disabled state, and live error announcements.
  • Data recipes own sorting, selection, expansion, pagination, virtualization, and data accuracy.
  • Feedback/loading recipes own queueing, timers, progress values, lifecycle, and announcements.

Validation

Example quality and release checks

Source truth and package-facing imports must stay aligned: authoring evidence lives under src/, while copyable consumer imports use dist/. Validate examples in narrow and wide viewports, active themes, reduced-motion, forced-colors, and high-contrast contexts.

  • Examples must remain source-backed, copy-safe, and realistic enough to adapt.
  • Application code owns runtime JavaScript, ARIA synchronization, focus, keyboard, routing, lifecycle, and announcements.
  • Responsive, theme, motion, and contrast behavior must be checked in the consuming layout.
  • Migration and release notes must record any changed selector, token, import, or example contract.
