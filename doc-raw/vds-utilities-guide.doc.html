Utilities Guide

Utilities are small composition helpers. They can adjust spacing, layout, visibility, and text treatment, but they do not create component behavior, semantics, or state.

Source truth

Utility imports

Utility selectors are authored in src/components/utilities.css and ship through dist/components/utilities.css. The selector reference remains the Utilities page. 

@import "@24vlh/vds/dist/core.css";
@import "@24vlh/vds/dist/components/utilities.css";

Example

Composition without replacing semantics

Use utilities to support layout around semantic markup. Do not use utilities to fake disabled, selected, invalid, hidden, or current state.

Deployment notes

Utilities support spacing and tone while the document keeps real structure.

Accessibility

Utility boundaries

A utility class cannot add keyboard behavior, ARIA synchronization, focus management, or live announcements.

  • Use sr-only helpers only for text that must remain available to assistive technology.
  • Use responsive utilities only when DOM order still makes sense.
  • Use component state classes or ARIA state for behavior, not visual utilities alone.
  • Record utility pruning, aliases, or renamed helpers in migration notes.

Validation

Example quality and release checks

Source truth and package-facing imports must stay aligned: authoring evidence lives under src/, while copyable consumer imports use dist/. Validate examples in narrow and wide viewports, active themes, reduced-motion, forced-colors, and high-contrast contexts.

  • Examples must remain source-backed, copy-safe, and realistic enough to adapt.
  • Application code owns runtime JavaScript, ARIA synchronization, focus, keyboard, routing, lifecycle, and announcements.
  • Responsive, theme, motion, and contrast behavior must be checked in the consuming layout.
  • Migration and release notes must record any changed selector, token, import, or example contract.
