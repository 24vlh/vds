Foundation

Base Layer

The base layer normalizes browser defaults, focus behavior, native controls, motion preferences, and forced-colors behavior before component CSS is loaded.

Source truth

Authoring and package surfaces

Base is authored in src/base.css. It ships through dist/core.css and dist/vds.css, not as a standalone dist/base.css file. 

@import "@24vlh/vds/dist/core.css";
@import "@24vlh/vds/dist/themes/graphite.css";

Load base through core.css when composing component-level imports. Load a theme after the VDS CSS surface so theme variables are available to components.

Contract

What base owns

Base owns document defaults and platform normalization. It does not replace semantic HTML, application state, or component-specific styles.

  • Sets the global box model and readable text defaults.
  • Normalizes focus-visible outlines and removes focus rings only when the browser says focus is not visible.
  • Respects prefers-reduced-motion and forced-colors.
  • Normalizes native buttons, form controls, tables, media, and SPA roots without adding behavior.

Copy-safe example

Native controls stay semantic

Base makes native controls predictable, but the app still owns labels, button types, validation, and submission. 

<form action="/settings" method="post">
  <label for="team-name">Team name</label>
  <input id="team-name" name="teamName" autocomplete="organization">
  <button type="submit">Save settings</button>
</form>

Use component form classes when you need VDS form styling. Base only keeps the native platform surface stable.

Accessibility

Runtime boundaries

Base provides focus and preference-aware defaults. Consumers still own semantic structure, labels, invalid state, announcements, routing, and keyboard behavior for custom widgets.

  • Use native elements before adding ARIA.
  • Add type to buttons in forms.
  • Pair status color with text.
  • Test custom themes against focus-visible, reduced motion, and forced-colors modes.

Validation

Example quality and release checks

Source truth and package-facing imports must stay aligned: authoring evidence lives under src/, while copyable consumer imports use dist/. Validate examples in narrow and wide viewports, active themes, reduced-motion, forced-colors, and high-contrast contexts.

  • Examples must remain source-backed, copy-safe, and realistic enough to adapt.
  • Application code owns runtime JavaScript, ARIA synchronization, focus, keyboard, routing, lifecycle, and announcements.
  • Responsive, theme, motion, and contrast behavior must be checked in the consuming layout.
  • Migration and release notes must record any changed selector, token, import, or example contract.
