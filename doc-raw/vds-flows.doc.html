Progression

Flows

Flow CSS styles steps, timelines, journeys, process nodes, branches, progress bars, and form-flow states. CSS owns presentation; application code owns current-step, validation, routing, and announcements.

Source truth

Imports and package surface

Flows are authored in src/components/flows.css and ship through dist/components/flows.css. 

@import "@24vlh/vds/dist/core.css";
@import "@24vlh/vds/dist/components/flows.css";

Example

Wizard progress

Use visible labels and synchronize current/complete/disabled state with the real task state.

  1. Draft
  2. Review
  3. Publish 
<ol class="steps" aria-label="Publish workflow">
  <li class="steps__item steps__item--active" aria-current="step">
    <span class="steps__label">Review</span>
  </li>
</ol>

Accessibility

State ownership

CSS does not advance steps, validate a form, route between stages, or announce progress changes.

  • Synchronize aria-current, aria-disabled, and progress values in application code.
  • Use ordered lists when order is meaningful.
  • Pair error, warning, and success states with text.
  • Announce validation and step changes when they happen without navigation.

Validation

Example quality and release checks

Source truth and package-facing imports must stay aligned: authoring evidence lives under src/, while copyable consumer imports use dist/. Validate examples in narrow and wide viewports, active themes, reduced-motion, forced-colors, and high-contrast contexts.

  • Examples must remain source-backed, copy-safe, and realistic enough to adapt.
  • Application code owns runtime JavaScript, ARIA synchronization, focus, keyboard, routing, lifecycle, and announcements.
  • Responsive, theme, motion, and contrast behavior must be checked in the consuming layout.
  • Migration and release notes must record any changed selector, token, import, or example contract.
